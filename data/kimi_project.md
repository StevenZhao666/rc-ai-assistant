1. **①安全与合规事故最可能直接让项目停掉**：公开模型入口可能被刷爆配额和账单，上传、审核或 MCP 中任何未鉴权的写／执行能力都可能导致篡改、挂马；无 HTTPS 又放大凭据和提问内容泄露，再叠加外部 API 的个资外发，足以触发校方关站。**②错误、过期或无出处答案被当作官方解释**，一次造成学生实际损失，就可能让书院撤回支持。**③不可恢复、不可交接**会慢性做废：若单机备份从未做恢复演练，内容又无法追溯到具体版本，一次故障或学生换届就可能无法继续维护。

2. 工程顺序定为：**轻量合数据 → 补内容 → 最小管理登录 → 接更多客户端**，但绝大部分工时给补内容；TLS、写接口临时封锁／鉴权、上传限制、模型限流与预算熔断、外发前最小化／脱敏，以及一次备份恢复演练，是第一周前置项，不等正式登录项目。“合数据”只做统一只读检索接口、固定字段和状态过滤，并用 30–50 条覆盖过期、无答案、跨来源场景的评测题锁住行为，**不做迁库**。随后按高频真实需求补内容，引用不到官方原文或已失效就明确拒答；公开问答继续免登录，审核端先用反代 Basic Auth／IP 白名单兜底，客户端等覆盖率和引用质量达标再接。

3. **赞成不物理合并，因为当前规模下迁移风险大于收益，但交付物应是具有统一来源、版本、状态和排序契约的只读检索接口；若“两份库”是两个独立 SQLite 文件，不要指望持久 SQL VIEW 跨库，直接在应用层实现。**

4. 现在就把**“内容版本与引用契约”设为所有入库、上架的强制门槛**：稳定 ID、revision／content_hash、官方来源与原文快照、生效／失效时间、状态、审核记录缺一不可，检索和模型只能使用已发布版本，回答只引用这些稳定 ID。以后无论合库、换检索或模型、接客户端，还是处理纠错投诉，都不必重洗历史数据，也能复现“当时依据哪一版”。审计日志默认只记引用版本和必要运行信息，不长期保存完整提问，避免顺带制造个资积压。
