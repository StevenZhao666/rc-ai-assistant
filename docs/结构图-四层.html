2資料庫：問答與原文分開存

一條知識＝一條可審核的斷言；原文是另一層，只加不改。檢索只吃 published 且未過期。

kb_item　問答層

  • question / answer　問題與答案
  • status　草稿→待審→發布→過期→歸檔
  • ttl_type　A 穩定 / B 年度 / C 實時
  • source_url　來源頁面
  • original_answer　導入時原文
  • source_chunk_id　綁定的條款
每條指向
一條條款

chunk　原文層

  • anchor　條款號（3.2）
  • section　章節（Visitors）
  • variant　zh / en
  • version　AY2026-2027
  • hash　內容指紋，重導不重複
  • text　條款正文

qa_log

  • 誰、問什麼、答什麼
  • mode 模式
  • latency_ms 耗時
  • n_cites 引用數

feedback

  • 👍 / 👎
  • note 用戶寫的原因
  • mode 當時模式

review_log

  • 誰、何時、做了什麼
  • action approve/bind…
  • before / after

candidate

  • 官網抓來的候選
  • status 待處理
  • item_id 轉正後

設想 · L3

3如果做成書院資料庫

不只服務昆昆，還要給別的專案、同學的 AI 用。關鍵是分層與版本。

① 原文層

規章、通知、手冊。帶版本、生效與廢止日期，只加不改，任何歷史版本可回溯。

新增：doc · doc_version · clause

② 知識層

問答、術語表、常見誤解。每條指向原文層的一段，可審核、可撤回。

新增：kb_item_ref · glossary

③ 入口層

API / MCP：誰能拿什麼、配額多少、每次調用留痕。

新增：client · api_log
表解決什麼問題
doc / doc_version現在版本資訊散在 chunk 裡，答不了「這條何時失效」「學生引的是哪一版」
clause把 chunk 兼任的職責拆開：文件 → 版本 → 條款
kb_item_ref一條問答可能靠兩條條款；現在只能綁一條。還要標「直接規定／解釋／參考」
client / api_log對外開放必須有身分、配額、審計；出事能追
glossaryHA、RC、High Table 這類術語，現在只能靠條目湊

對外只讀介面建議先開四個：search_kb、get_item、get_clause、list_updates。MCP 就是把它們包一層。
