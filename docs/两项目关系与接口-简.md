# 两个项目：边界、联系与对外接口

回答三个问题：**哪两个项目、怎么分开、怎么连起来**；**CKLCdb 现在能干什么**；**别人怎么接**（读 API / 写 API / MCP）。

---

## 一、是哪两个

| | A · 崑崑问答 | B · CKLCdb 资料库 |
|---|---|---|
| 面向 | 学生提问，要一个能核对的答案 | 存书院产出的内容（规章、作品、网站、文件） |
| 入口 | `/` | `/library`、`/upload`、`/review?tab=uploads` |
| 数据表 | `kb_item`、`chunk`、`kb_revision` | `library_item`、`upload_file`、`chunk_revision` |
| 核心动作 | 检索 → 生成 → 带引用回答 | 投稿 → 审核 → 上架 → 浏览/下载 |
| 输出 | 一段话 + `[n]` 依据 | 条目 + 文件 + 可检索的元数据 |

## 二、独立性：哪些是真的分开

**代码不互相 import。** `answer.py` / `retrieve.py` 里没有任何 `library` 相关调用；`library.py` / `upload.py` 也不 import `answer`。两边各自挂 `APIRouter`，各自有页面。

**业务表分开。** 问答只读 `kb_item` + `chunk`；资料库读写 `library_item` + `upload_file`。归档、下架、版本历史都各走各的。

**发布可以分开。** 改 A 的提示词不影响 B 的审核流程；B 的投稿页挂了，A 照常回答。

## 三、联系性：哪些是共用的（这里最容易被说错）

**同一个进程、同一个 SQLite 文件。** 不是两个网站，是同一套 `app` 的两组路由，跑在同一个 `uvicorn`（8091）里，读写同一个 `data/kb.sqlite3`。合并部署的原因很实际：2 核 4G，省一份内存和连接池。代价是发布绑在一起——改一边要重启整个服务。

**共用底座**：`db.py`（连接、迁移、检索）、`auth.py`（`REVIEWERS` 名单）、`i18n.py`、`config.py`。

**有共用表，而且不止一张**：

| 表 | 谁写 | 说明 |
|---|---|---|
| `candidate` | `upload.py`（投稿）、`review.py`（抓取候选） | 两边都进同一个候选池 |
| `review_log` | 两边的审核动作 | 同一份审计流水 |
| `qa_log` / `feedback` | 问答侧 | 资料库不读 |

所以"两张表完全分开"是不准确的说法。准确说法是：**主数据表分开，审核与候选这类流程表共用**。

**跨项目的读，走应用层聚合，不是数据库视图**：

- `GET /api/search?q=`：一次查 `kb_item` + `library_item`，问答结果加权，统一返回带 `type` 的列表
- `GET /api/updates?since=`：同时返回 `{qa: [...], library: [...]}`
- 审核页的"规章原文自动匹配"：B 的审核界面会读 A 的 `chunk` 表（按条款号/全文）

一句话：**代码不互相调用，数据面通过同一份库和应用层聚合接口连起来。**

## 四、CKLCdb 现在能干什么

| 能力 | 状态 | 入口 |
|---|---|---|
| 投稿（作品/网站/文件，邀请码） | 可用 | `POST /api/upload` |
| 审核（通过/退回，退回必填理由） | 可用 | `/review?tab=uploads` |
| 上架浏览（繁简英、类型筛选、关键词） | 可用 | `/library` |
| 文件下载 | 可用 | `/files/...`、`/files-download/{id}` |
| 公开检索（问答+资料库同框） | 可用 | `/api/search` |
| 文件元数据检索 | 可用 | `/api/files` |
| 下架（不删行、不删文件） | 可用 | `POST /api/review/library/{id}/archive` |
| 邮箱公开可控 | 可用 | 投稿时勾选，默认不公开 |
| 版本留痕 | 已建，未用 | `revision` / `content_hash` / 历史表 |

**现在线上资料库是空的**：23 条测试数据全部 `archived`，等真投稿。这不是故障。

## 五、对接接口（给别的项目用）

### 读：公开、无需登录（按 IP 限速）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/search?q=&limit=` | 统一检索，返回 `type=qa/work/link/doc` |
| GET | `/api/library?kind=&q=&limit=` | 资料库列表 + 分类计数 |
| GET | `/api/library/{id}` | 单条（邮箱按公开设置决定是否下发） |
| GET | `/api/files?q=&kind=&limit=` | 文件列表（只在已上架条目里） |
| GET | `/api/files/{id}` | 单个文件元数据 |
| GET | `/files-download/{id}` | 下载（带原文件名） |
| GET | `/api/qa/{id}` | 问答单条（含 `uid`/`revision`/`content_hash`） |
| GET | `/api/clauses?q=` | 条款全文检索（FTS5） |
| GET | `/api/clause?anchor=3.2&version=` | 按条款号取原文 |
| GET | `/api/updates?since=2026-11-01` | 近期变更（问答 + 资料库） |

### 写：目前只有"人"能写，没有对外写接口

| 方法 | 路径 | 认证 |
|---|---|---|
| POST | `/api/upload` | 邀请码 `UPLOAD_CODE` |
| POST | `/api/review/uploads/{id}/decide` | `X-Reviewer` 头 + 白名单 |
| POST | `/api/review/library/{id}/archive` | 同上 |
| POST | `/api/review/item/{id}/decide` | 同上（问答库，**别拿它下架资料库**） |

**没有 API Key、没有按项目配额、审核接口只认一个可伪造的请求头。** 这是目前对接别的项目时最大的洞：任何知道地址的人都能发 `X-Reviewer: <白名单学号>`。上正式对接前必须补：反代 Basic Auth / IP 白名单，或改成签名令牌。

### MCP（只读，已上线）

| 端点 | 工具 | 用途 |
|---|---|---|
| `http://159.75.225.125/ai/mcp` | `search_kb`、`search_clauses`、`get_item`、`get_clause`、`list_updates` | 问答 + 条款 |
| `http://159.75.225.125/ai/mcp-files` | `search_files`、`get_file`、`list_files` | 资料库文件 |

两个都是 **Streamable HTTP、只读、无身份**（按 IP 限速 60/分）。MCP 服务本身不 import 业务模块，只用 HTTP 打回 8091，所以它可以独立重启。

**写 MCP 没有做，也不建议现在做**：写接口连身份都没有，包成 MCP 等于把审核权限发给任何客户端。

## 六、给不同对接方的建议

| 对接方 | 用哪条 | 备注 |
|---|---|---|
| 同学的 AI（Claude/Cursor/Cherry） | MCP `/ai/mcp` | 零安装，只读 |
| 学生社团自己的网站 | `GET /api/library` + `/api/search` | 只读，建议加缓存 |
| 论坛（收文件） | `POST /api/upload` + 邀请码 | 上传后仍需人工审核 |
| 需要写入的其他系统 | 暂缓 | 先补 API Key 与审计，再开写接口 |

## 七、已知缺口（按优先级）

1. **写接口无身份**：`X-Reviewer` 可伪造 → 先上反代 Basic Auth 或令牌
2. **无 HTTPS**：裸 IP + HTTP，投稿邮箱和提问内容明文传输
3. **资料库空**：没有真内容，演示只能看流程
4. **两库未合并**：统一检索是应用层拼的，字段契约靠代码约束
5. **无 per-client 配额**：所有外部调用共享同一个 IP 限速
