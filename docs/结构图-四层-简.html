2资料库：问答与原文分开存

一条知识＝一条可审核的断言；原文是另一层，只加不改。检索只吃 published 且未过期。

kb_item　问答层

  • question / answer　问题与答案
  • status　草稿→待审→发布→过期→归档
  • ttl_type　A 稳定 / B 年度 / C 实时
  • source_url　来源页面
  • original_answer　导入时原文
  • source_chunk_id　绑定的条款
每条指向
一条条款

chunk　原文层

  • anchor　条款号（3.2）
  • section　章节（Visitors）
  • variant　zh / en
  • version　AY2026-2027
  • hash　内容指纹，重导不重复
  • text　条款正文

qa_log

  • 谁、问什么、答什么
  • mode 模式
  • latency_ms 耗时
  • n_cites 引用数

feedback

  • 👍 / 👎
  • note 用户写的原因
  • mode 当时模式

review_log

  • 谁、何时、做了什么
  • action approve/bind…
  • before / after

candidate

  • 官网抓来的候选
  • status 待处理
  • item_id 转正后

设想 · L3

3如果做成书院资料库

不只服务昆昆，还要给别的专案、同学的 AI 用。关键是分层与版本。

① 原文层

规章、通知、手册。带版本、生效与废止日期，只加不改，任何历史版本可回溯。

新增：doc · doc_version · clause

② 知识层

问答、术语表、常见误解。每条指向原文层的一段，可审核、可撤回。

新增：kb_item_ref · glossary

③ 入口层

API / MCP：谁能拿什么、配额多少、每次调用留痕。

新增：client · api_log
表解决什么问题
doc / doc_version现在版本资讯散在 chunk 里，答不了「这条何时失效」「学生引的是哪一版」
clause把 chunk 兼任的职责拆开：文件 → 版本 → 条款
kb_item_ref一条问答可能靠两条条款；现在只能绑一条。还要标「直接规定／解释／参考」
client / api_log对外开放必须有身分、配额、审计；出事能追
glossaryHA、RC、High Table 这类术语，现在只能靠条目凑

对外只读介面建议先开四个：search_kb、get_item、get_clause、list_updates。MCP 就是把它们包一层。
