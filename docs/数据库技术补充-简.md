# 数据库技术补充：CKLCdb 在硬盘上到底是什么样

*一个 1 MB 的文件，十一张表，两套检索。*

> **本文基于写作时的实测快照（`data/kb.sqlite3`，1,101,824 字节 / 269 页）写成。**
> 服务在跑，页数和行数会小幅增长——你照着敲命令时看到 270 页、886 条 `qa_log` 是正常的。
> 项目介绍、接口说明、产品功能在别的文档里；这一篇只讲**数据库**——它怎么存、怎么读、怎么坏、怎么救。
> 文中所有 `PRAGMA`、`EXPLAIN QUERY PLAN`、报错信息都是在本机真实跑出来的输出，不是示意。

---

## 1. 先看清楚我们要讲的东西

### 1.1 这个项目的数据，其实只有四类

| 类别 | 在哪 | 在里面干什么 |
|---|---|---|
| **制度原文** | `chunk` | 《住宿规章》《学生手册》切成一条条条款，供回答引用 |
| **问答条目** | `kb_item` | 一条问题 + 一条答案 + 一条来源，人工审核过 |
| **资料库内容** | `library_item` + `upload_file` + `candidate` | 院生投稿的作品/网站/文件，走投稿→审核→上架 |
| **流水与痕迹** | `qa_log`、`feedback`、`review_log`、`kb_revision` | 谁问过什么、谁点了没用、谁什么时候批了哪条 |

前三类是**资产**（丢了就没了），第四类是**证据**（丢了可以重来，但没有它就不知道当初为什么这么改）。这个区分决定了后面"哪些必须备份、哪些可以重建"。

### 1.2 为什么是 SQLite，而且是一个文件

三个理由：**规模不够格上服务器**（全部数据 1 MB，MySQL 一个空实例就要几百 MB 内存）；**部署要能拷一个文件夹就走**（最坏情况是一台 Windows 机器 + 一个共享盘，SQLite 拷贝即迁移）；**备份可以蠢到极致**（`Copy-Item` 一句就是完整备份，真写在 `scripts/start_all.bat` 里）。

## 2. 硬盘上的一个文件

### 2.1 1,101,824 这个数字是怎么来的

在项目根目录跑：

```bash
.venv/Scripts/python.exe -c "
import sqlite3
c = sqlite3.connect('data/kb.sqlite3')
for p in ('page_size', 'page_count', 'freelist_count'):
    print(p, '=', c.execute(f'PRAGMA {p}').fetchone()[0])
"
```

真实输出：

```
page_size = 4096
page_count = 269
freelist_count = 0
```

`4096 × 269 = 1,101,824` —— 和 `ls -la` 看到的文件大小**一个字节都不差**。

这不是巧合，是 SQLite 的存储模型：**数据库文件就是一堆等长的页（page）首尾相接排在一起**。页是最小读写单位，默认 4096 字节（4 KB）。第 0 页特殊（存文件头），从第 1 页开始才是真正的数据。

`freelist_count = 0` 表示此刻没有空闲页——删数据不会缩小文件，被删的页会进空闲链表等着复用（7.3 的 `VACUUM` 就是清它）。

### 2.2 页里面装的是 B-tree

页内部不是行平铺，而是 **B-tree 节点**。SQLite 只有两种组织方式：**表本身是一棵 B-tree**（按 `rowid` 排序，叶子存整行），**每个索引也是一棵独立的 B-tree**（叶子存"索引列 → rowid"）。

所以 `id` 是 `INTEGER PRIMARY KEY AUTOINCREMENT` 时特别快：`id` 直接就是 rowid，走一趟主 B-tree 就到了。也是为什么加索引能提速：没索引只能从第 1 页扫到第 269 页，有索引就走一趟小得多的树。

### 2.3 journal 模式：这个库**没有**开 WAL

很多人想当然。实测 `PRAGMA journal_mode` 返回 `delete`——默认的 rollback journal，不是 WAL。代码里没有任何地方执行 `PRAGMA journal_mode=WAL`，`connect()` 只做了三件事：建目录、`sqlite3.connect(..., timeout=10)`、设 `row_factory`。

两种模式的区别：

| | rollback journal（当前） | WAL |
|---|---|---|
| 写的时候 | 先把**原始页**拷进 `-journal`，再改主库；提交时删掉 | 写进 `-wal`，主库不动；读的人从 `-wal` 补 |
| 读写能否并行 | **不能**，写锁挡住读 | 能 |
| 磁盘上多出 | 事务期间出现 `-journal`，结束就没了 | 常驻 `-wal` + `-shm` |

**为什么没切 WAL？** 收益接近零、风险不为零：写入点全是"人点一下"，冲突概率极低；uvicorn 单进程，每次操作**新开连接**，不存在一堆连接抢锁；而运维动作是"拷一个文件就备份"——`start_all.bat` 那句 `Copy-Item` 在 delete 模式下是**完整**的，换成 WAL 后若恰有未 checkpoint 的事务，只拷主文件会丢数据。

**结论：等真的出现"读被写卡住"再切，切的时候记得同时改备份脚本。**

### 2.4 `-wal` / `-shm` / `-journal` 什么时候才出现

现在 `data/` 里**一个都没有**（`ls data/ | grep -Ei 'wal|shm|journal'` 无输出）。出现时机：

| 文件 | 什么时候在 | 什么时候消失 |
|---|---|---|
| `kb.sqlite3-journal` | 一个写事务进行中 | 提交/回滚后自动删除 |
| `kb.sqlite3-wal` | 切到 WAL 后**一直**在 | `wal_checkpoint(TRUNCATE)` 后变 0 字节，文件还在 |
| `kb.sqlite3-shm` | WAL 模式下有连接打开时 | 最后一个连接关闭后自动删 |

**踩坑预警**：如果在 `data/` 看到 `kb.sqlite3-journal` 静静躺着、服务又已经停了，说明上次写事务**中途崩了**。别删它——下次打开时 SQLite 会用这个 journal 自动回滚到一致状态。删了它，你得到一个"能打开、实际半写不写"的库。

顺带记几个文件头里的值（`PRAGMA schema_version` / `encoding` / `auto_vacuum`）：`encoding = UTF-8` 是"張崑崙"能保留繁体不被转码的前提；`schema_version = 58` 表示库结构被改过 58 次（每次 `ALTER`/`CREATE` 加一，这是 SQLite 内部的**结构**版本号，不是业务版本）；`auto_vacuum = 0` 表示删掉的空间只留在 freelist 里复用，这就是 7.3 要 `VACUUM` 的原因。

### 3.2 `kb_item`：一条知识 = 一条断言

这是全项目的核心表。设计上最关键的一句话写在 `app/db.py` 开头：**一条知识 = 一条「断言」，不是一份文档。**

一份文档是"《住宿规章》全文"；一条断言是"书院不允许在房间养宠物，依据 17.1"。后者才能被检索、被审核、被追责。

```sql
CREATE TABLE IF NOT EXISTS kb_item (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    question    TEXT NOT NULL,
    answer      TEXT NOT NULL,
    category    TEXT,
    source      TEXT,              -- 来源说明，如《住宿规章》第 4.2 条
    source_url  TEXT,
    source_type TEXT DEFAULT 'unverified',  -- official / external / unverified
    note        TEXT,              -- 修改原因
    status      TEXT NOT NULL DEFAULT 'published',
    ttl_type    TEXT NOT NULL DEFAULT 'A',
    audience    TEXT NOT NULL DEFAULT 'all',
    owner       TEXT,
    reviewer    TEXT,
    verified_at TEXT,
    valid_until TEXT,
    warnings    TEXT,              -- JSON 数组
    original_answer TEXT,          -- 导入时的原文
    source_anchor TEXT,            -- 绑定的规章条款号，如 3.2
    created_at  TEXT NOT NULL
);
```

加上 `_migrate()` 后补的列，实际共 **29 列**。挑关键的说：

**`status` 是状态机，不是标签**：`draft / review / published / expired / archived`。**`ttl_type` 决定答案能活多久**：A 稳定（办公室在哪）、B 年度型（今年住宿费）、C 实时（本周菜单），当前 A 126 / B 7 / C 7；它不参与检索过滤，但驱动复核队列——`list_recheck()` 里 B 类优先被翻出来。检索**只吃 `published`**——`published_items()` 里那句 `WHERE status='published'` 是硬约束。审核不是流程装饰，而是"能不能被人看见的开关"。当前实测 `published 119 / archived 21`。

**三套时间字段是演进痕迹，不是冗余。** `valid_until` 是早期字段；`effective_from`/`effective_to` 是后加的"内容版本契约"——回答"2026 年 8 月才生效"的新规章时，旧答案不该消失，只是暂时不返回。检索 SQL 同时判三者，`?` 都填今天。新代码优先用 `effective_*`。

**`uid` / `revision` / `content_hash` 是对外承诺。** `uid` 形如 `kb-0001`，永不变；`revision` 是内容第几版；`content_hash` 是 `sha1(question+"\n"+answer)[:12]`。前端折叠区显示 `v3 · 2026-08-01 起生效 · a1b2c3`，学生申诉时能对上号。实测一行：

```
{'id': 3, 'uid': 'kb-0003', 'revision': 1, 'content_hash': '8a7d7428db7f',
 'status': 'published', 'ttl_type': 'A', 'source_anchor': '2.1',
 'source_chunk_id': 767, 'q': '張崑崙書院辦公室能做什麼？'}
```

注意 `source_anchor` 和 `source_chunk_id` 同时存在——**两种绑定方式，后者更牢**。条款号 `2.1` 在《学生手册》和《住宿规章》里可能各有一条（`chunk` 用 `section` 区分），按号找会撞车；`source_chunk_id` 直接指向 `chunk.id`，不受同号干扰。

**`warnings` 是 JSON 字符串不是表。** SQLite 没有数组类型，用 TEXT 存 JSON 是常规做法，代价是查不了内部结构（只能 `LIKE`）。读出来都会 `json.loads`，脏数据被 `try/except` 兜成 `[]`。

**`version` 和 `revision` 是两个完全不同的计数器**，这是全表最容易搞混的地方：

| 字段 | 谁在改 | 干什么用 |
|---|---|---|
| `version` | 每次审批动作 +1（`decide_item`） | **乐观锁**：提交时版本对不上 → `conflict`，防覆盖 |
| `revision` | 只有正文 hash 变了才 +1（`bump_kb_revision`） | **内容版本**：对外引用、历史归档 |

前者管并发，后者管内容。混用会导致"改个错别字就涨版本号"或者"两人同时改互相覆盖"。

### 3.3 `chunk`：规章条款的原子单位

```sql
CREATE TABLE IF NOT EXISTS chunk (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    url TEXT, title TEXT, text TEXT,
    status     TEXT DEFAULT 'draft',
    updated_at TEXT,
    anchor     TEXT,              -- 条款号，如 4.2
    version    TEXT,              -- 规章版本，如 AY2026-2027
    source     TEXT,              -- 文件名 + 哈希
    section    TEXT,              -- 所属章节，区分同号条款
    variant    TEXT,              -- zh / en
    hash       TEXT               -- 内容指纹，用于判重
);
```

十八列（含迁移加的 `uid/revision/content_hash/effective_*`）。

**`anchor + section + variant` 三个一起才唯一。** 实测数据里就有陷阱：

```
id=568  anchor=1.1  variant=en  section='1. General'
id=570  anchor=1.3  variant=zh  section='1. General'
id=571  anchor=1.2  variant=zh  section='1. General'
```

同一条规章有中英两份（`variant`），不同章节可能有同一个条款号（`section`）。所以 `get_clause(anchor)` 的注释写着"同一号有中英两条时全部返回"——它返回列表，调用方自己挑。

**`version` 是规章版本号，不是 `revision`。** 实测分布：`AY2026-2027` 240 条、`R0001/2020` 36、`R0002/2020` 28、`R0003/2020/V3` 30、`R0004/2019` 28、`R0007/2019` 6。这就是"同一条款、不同学年"能共存的原因：`get_clause(anchor, version="AY2026-2027")` 带版本就只查那一版。

**`hash` 和 `content_hash` 是两个指纹。** 前者是导入时的判重指纹（"这条我导过了吗"），后者是版本契约的正文指纹（"这条内容变了没"）。前者防重复导入，后者防无意义改版。

### 3.4 `chunk_fts`：一个虚拟表，带着五个影子表

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS chunk_fts USING fts5(
    uid UNINDEXED, anchor UNINDEXED, version UNINDEXED, source UNINDEXED, body);
```

拆开读：

- **`USING fts5`** = 全文索引，不是普通表。`body` 会被切成词进倒排索引。
- **`UNINDEXED`** = 这四列只存不索引。`uid/anchor/version/source` 是回表定位用的元数据，不需要被搜。不加这个标记，`kb-0003` 会被当词切碎，污染结果还白占空间。
- **`body`** = 唯一被索引的列，里面存的**不是原文**，是切好的二元组字符串（4.2 节）。

**一个常被误解的点：这份索引存了两份正文。** `sqlite_master` 里除了 `chunk_fts` 还有：

```
chunk_fts_data     倒排索引本体（B-tree，block BLOB）    25 行 / 102 KB
chunk_fts_idx      倒排索引的分段目录                    23 行
chunk_fts_content  正文副本（因为没写 content=''）        368 行 / 135 KB
chunk_fts_docsize  每篇文档长度（bm25 要用）              368 行
chunk_fts_config   配置（tokenizer 等）                      1 行
```

`chunk_fts_content` 有 368 行、占 135 KB——正文真存了两份：一份在 `chunk.text`，一份在这里。**为什么不改成 external content 表省空间？** 因为 `body` 存的不是原文而是 `_bigrams()` 的结果，FTS5 的 `content=chunk` 模式要求两边逐字一致，从一开始就不一致，省不掉。368 条才 135 KB，不值得为此改设计。

### 3.5 `library_item`：资料库的上架条目

```sql
CREATE TABLE IF NOT EXISTS library_item (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    candidate_id INTEGER, kind TEXT, title TEXT NOT NULL,
    author TEXT, contact TEXT, note TEXT,
    file_ids TEXT,              -- JSON 数组
    status TEXT DEFAULT 'published',
    created_at TEXT, reviewer TEXT, reviewed_at TEXT
);
```

迁移又加了 `contact_public INTEGER DEFAULT 0`。三个选择值得说：

**`file_ids` 是 JSON 字符串，不是关联表。** 一个条目最多挂 3 个附件（`UPLOAD_MAX_FILES`），为此建 `item_file` 关联表，收益是"能写 JOIN"，成本是每次读写都得管两处。**在"最多 3 个"这种硬上限下，JSON 数组是更诚实的选择**。代价是 `library_items()` 读完要再 `_files_of(ids)` 补一次 `WHERE id IN (...)`——典型 N+1，但 N 极小。

**`candidate_id` 是软链接，不是外键。** 它指向 `candidate.id` 但没有 `REFERENCES`，因为候选会被清理、上架条目必须永久保留。硬外键会让"清理候选池"变成不可能。

**`contact_public` 默认 0，是隐私开关：**

```python
if not int(r.get("contact_public") or 0):
    r.pop("contact", None)          # 没选公开，就不对外返回邮箱
```

**过滤在 Python 层做，不在 SQL 层**——宁可多读一列再删，也不写两套 SELECT。所以读 `library_item` 一律走 `library_items()`，别自己 `SELECT *`。

### 3.6 `upload_file`：只存路径和指纹，不存二进制

```sql
CREATE TABLE IF NOT EXISTS upload_file (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sha256 TEXT NOT NULL, path TEXT NOT NULL,
    orig_name TEXT, mime TEXT, size_bytes INTEGER, created_at TEXT
);
```

实测三行（`data/files/` 目前 13 KB、6 个文件）：

```
1  add9cf0e9ce3  files/inbox/202611/add9cf0e9ce3.pdf   demo.pdf           43 B
2  8a5d8b28d66a  files/inbox/202611/8a5d8b28d66a.md    x0.md               4 B
3  9951e49718b2  files/inbox/202611/9951e49718b2.png   kunkun-student.png  1715 B
```

**`path` 是相对 `DATA_DIR` 的路径**，不是绝对路径。这一条决定了三件事：整库搬到新机器（`D:\` → `/opt/`）不用改任何数据；Web URL 是砍掉 `files/` 前缀拼出来的（`"/files/" + path.split("files/", 1)[-1]`）；附件 404 的根因通常就在这条链上（8.4 节）。

**`sha256` 是去重键。** `add_file()` 先 `WHERE sha256=?`，命中就直接返回旧 id——同一个文件传两次只存一份。文件名本身也是哈希前 12 位（`f"{sha[:12]}{ext}"`）。

**但 `sha256` 上没索引。** 六行数据无所谓；投稿量上来后这个查询会全表扫。加一条 `CREATE INDEX` 是一行的事，**现在不加**——过早优化会让"表结构最小"这个原则先破掉。

### 3.7 `candidate`：投稿和抓取共用一个池子

最容易被误解的表。它同时装着两种来源完全不同的东西：

| `source` | 谁写的 | `status` 取值 |
|---|---|---|
| `upload` | `upload.py` 的学生投稿 | `pending` → `approved` / `rejected` |
| 其他（URL 抓取） | 抓取脚本 | `new` → `accepted` / `rejected` |

```sql
CREATE TABLE IF NOT EXISTS candidate (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    url TEXT NOT NULL, title TEXT, text TEXT, source TEXT,
    status TEXT NOT NULL DEFAULT 'new', created_at TEXT,
    reviewer TEXT, note TEXT,
    item_id INTEGER           -- 采纳后生成的目标条目 id
);
```

迁移后补了 `kind / author / contact / file_ids / ip / contact_public`。

`url TEXT NOT NULL` 是第一版留下的约束——那时候选只有"从官网抓来的页面"，URL 必填。后来加了投稿（没有 URL），`add_upload_candidate()` 只好写空串 `("", title, note, "upload", ...)` 塞进去。

**这是一个真实的"演进疤痕"**：列约束没法用 `ALTER TABLE` 改（SQLite 不支持 drop constraint），要改只能重建表。目前用空串兼容，能跑，但意味着**别指望 `url` 一定非空**——写查询用 `WHERE url <> ''` 而不是 `WHERE url IS NOT NULL`。

共用池子的好处很实际：审核界面只有一个待办队列，审计流水 `review_log` 也只有一份。

### 3.8 `review_log`：谁、什么时候、把哪条、从什么改成什么

```sql
CREATE TABLE IF NOT EXISTS review_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts TEXT NOT NULL, item_id INTEGER, action TEXT NOT NULL,
    reviewer TEXT, note TEXT,
    before TEXT,               -- JSON：改前快照
    after  TEXT                -- JSON：改后快照
);
```

166 行、69 KB，是全库第二"重"的流水表。

**`before` / `after` 存整行 JSON 快照，不是 diff。** 这是刻意的笨办法：diff 需要 schema 感知（哪些字段该比、JSON 怎么比），快照只要 `json.dumps(dict(row))`。代价是空间——一次审批写两条整记录，平均一条 400 字节，完全可接受。

### 3.9 `kb_revision` / `chunk_revision`：版本历史

```sql
CREATE TABLE IF NOT EXISTS kb_revision (
    uid TEXT, revision INTEGER, content_hash TEXT, question TEXT, answer TEXT,
    status TEXT, changed_by TEXT, changed_at TEXT, note TEXT,
    PRIMARY KEY (uid, revision));

CREATE TABLE IF NOT EXISTS chunk_revision (
    uid TEXT, revision INTEGER, content_hash TEXT, text TEXT, anchor TEXT,
    version TEXT, changed_by TEXT, changed_at TEXT, note TEXT,
    PRIMARY KEY (uid, revision));
```

**复合主键 `(uid, revision)` 是这两张表唯一的技术亮点**，它同时做三件事：

1. **唯一性**：同一 uid 的同一版只能一行，重复写被 `INSERT OR REPLACE` 干掉
2. **聚簇**：自动建 `sqlite_autoindex_*`，按 `(uid, revision)` 排序——查"某条的完整历史"是**一次范围扫描**，不是全表扫
3. **幂等**：`INSERT OR REPLACE` 天然可重复执行

**两张表当前都是 0 行。** 原因见 6.5，那里有个真实发现。

### 3.10 `qa_log` / `feedback`：既进库又进文件

`qa_log` 11 列、880 行、占 262 KB——**全库最大的单表**（比 368 条规章的 `chunk` 还大），因为每条都存了完整的 question + answer。

```sql
CREATE TABLE IF NOT EXISTS qa_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts TEXT, student_id TEXT, question TEXT, answer TEXT,
    top_score REAL, feedback INTEGER,
    mode TEXT,            -- llm:xxx / basic / fallback_live / chat
```

`mode`、`latency_ms`、`session_id`、`n_cites` 都是迁移后补的——起初只记"谁问了什么、答案是什么、分数多少"，后来要看"是模型答的还是兜底答的、慢在哪、引了几条"，才一列一列加。**这就是 `_migrate()` 存在的意义。**

**关键设计：同一份数据写两处。**

```python
conn.execute("INSERT INTO qa_log (...) VALUES (...)", (...))
# 同时写一份 append-only 的流水：库被删/重建也不影响这份记录
with (config.DATA_DIR / "qa_log.jsonl").open("a", encoding="utf-8") as f:
```

库里那行**结构化、可查询**；JSONL 那行是**幸存者**——库被误删、被旧备份覆盖、迁移失败，这份纯文本还在。当前 `qa_log.jsonl` 847 行、`qa_log` 表 880 行（不等是早期数据没进 jsonl，正常的历史错位）。

`feedback` 8 列只 6 行（`vote` = 1 / -1 + 可选 `note`）。价值不在数量，而在 `bad_feedback()` 那句 `WHERE vote = -1`——被点"没用"的问题就是下一批要改的清单。

### 3.11 为什么整库没有外键

`PRAGMA foreign_keys = 0`，`CREATE TABLE` 里一个 `REFERENCES` 都没有。明确的取舍：

**不用的理由：** ① **导入顺序不受约束**——抓取脚本先写 `chunk`，再写 `kb_item`（带 `source_chunk_id`），再回灌 `chunk_fts`，有外键就得严格排序；② **软引用是业务需要**——条款每年更新，旧版归档后引用它的条目必须还在，硬外键会禁止"标记归档"；③ **`file_ids` 是 JSON 数组**，外键管不了。

**代价（必须承认）：** 引用完整性全靠应用层自觉。删 `chunk` 不会连带清 `kb_item.source_chunk_id`，可能出现"引用了不存在条款"的条目。缓解手段是**不删行**——`archive_library_item()` 只改 `status`，`chunk` 只标 `archived`。**本项目的事实标准是"永不 DELETE"**，这就把外键的必要性消掉了大半。

### 4.2 FTS5 为什么不自己做中文分词

SQLite 内置的 `unicode61` 分词器按空格和标点切词。中文没有空格，一整个句子会被当成一个"词"——搜"宠物"永远匹配不到"書院不允許飼養寵物"。

三条路摆在这儿：装 `simple`/`icu` 分词器扩展（要编 C 扩展，Windows 上分发是噩梦）；用 `jieba` 在 Python 里切好词再存（多一个依赖、对繁体支持一般、切错了就无法召回）；**自己切二元组存进去**（索引变大，但零依赖、零维护、召回率最高）。

选了第三条。核心就 8 行：

```python
def _bigrams(text: str) -> str:
    """中文切成重叠二元组，英文/数字保留整词；结果用空格分隔，喂给 FTS5。"""
    t = (text or "").lower()
    out: list[str] = []
    for run in re.findall(r"[一-鿿]+", t):
        if len(run) == 1:
            out.append(run)
        out += [run[i:i + 2] for i in range(len(run) - 1)]
    out += re.findall(r"[a-z0-9]{2,}", t)
    return " ".join(out)
```

实测：

```bash
.venv/Scripts/python.exe -c "
import sys; sys.path.insert(0,'.')
from app.db import _bigrams
print(repr(_bigrams('可以養寵物嗎')))
print(repr(_bigrams('换房间 pet policy 2026')))
"
```

```
'可以 以養 養寵 寵物 物嗎'
'换房 房间 pet policy 2026'
```

**"重叠"是关键。** `可以養寵物嗎` 六个字切出五个二元组，相邻两个字符一定会出现在**同一个**二元组里。这意味着：

- 搜"寵物" → 词 `寵物` 直接命中
- 搜"養寵" → 也命中
- 搜"可以養" → `可以` 和 `以養` 都命中

**唯一漏掉的情况：单字查询。** 搜"猫"，`_bigrams('猫')` 返回 `'猫'`（长度 1 的那个分支），能命中——但只有"猫"这个字独立成段时才进索引。这是可接受的边界。

### 4.3 检索的完整链路：AND → OR → bm25

`search_chunks()` 是唯一的全文入口，逻辑分三层：

```python
def search_chunks(q: str, limit: int = 5) -> list[dict]:
    toks = _bigrams(q)
    if not toks.strip():
        return []
    parts = toks.split()
    sql = ("SELECT f.uid, f.anchor, f.version, f.source, c.text, c.title, bm25(chunk_fts) AS rank"
           " FROM chunk_fts f JOIN chunk c ON c.uid = f.uid"
           " WHERE chunk_fts MATCH ? ORDER BY rank LIMIT ?")
    rows = []
    with connect() as conn:
        conn.row_factory = sqlite3.Row
        # 先 AND（准），没有再 OR（全）——中文换词很常见，纯 AND 会漏
        for expr in (" AND ".join(parts), " OR ".join(parts)):
            try:
                rows = conn.execute(sql, (expr, limit)).fetchall()
            except sqlite3.OperationalError:
                rows = []
            if rows:
                break
    return [...]
```

**第一层：AND 优先。** 问"訪客能不能過夜"切成 `訪客 客能 能不 不能 能過 過夜`，要求**所有**二元组都出现——这几乎是精确匹配，命中就一定相关。

**第二层：AND 落空就 OR。** 中文的表达弹性极大，"洗衣房几点开"和"洗衣房開放時間"只有 3 个二元组重合。纯 AND 会漏掉所有换了说法的问法，OR 保证"只要沾边就能召回"。

**第三层：`ORDER BY rank` 就是 bm25 排序。** `bm25(chunk_fts)` 返回**负数**，越小（越负）越相关，所以直接升序排、最后取负号变成正分：

```python
"score": round(-r["rank"], 2)
```

实测一条：

```bash
.venv/Scripts/python.exe -c "

from app.db import _bigrams
c=sqlite3.connect('data/kb.sqlite3')
e=' OR '.join(_bigrams('寵物').split())
for r in c.execute('SELECT f.uid,f.anchor,f.version,round(bm25(chunk_fts),4) rank '
                   'FROM chunk_fts f WHERE chunk_fts MATCH ? ORDER BY rank LIMIT 3',(e,)):
    print(r)
"
```

```
('chunk-0731', '17.1', 'AY2026-2027', -4.8937)
('chunk-0732', '17.1', 'AY2026-2027', -4.2924)
```

为什么 17.1 排前面？因为 bm25 会奖励**词频高、文档短**的匹配。同一条款的英文版（chunk-0731）和中文版（chunk-0732）都在，谁的字少、词更集中，谁的分更高。

**这一层还有个副产品：`JOIN chunk c ON c.uid = f.uid` 没有过滤 `status`。** 也就是说 `archived` 的条款也可能被搜出来。当前 368 条 `chunk` 全是 `published`，所以看不出问题；一旦开始归档旧学年条款，这里需要补一个 `AND c.status='published'`。

### 4.4 一个真实的坑：FTS 层不做繁简归一

这是我在实测中发现的，值得单独写一节，因为它解释了"为什么明明有这条内容却搜不到"。

`app/db.py` 里有两个 `_tokens()` 定义（同名，后者覆盖前者）和两个归一化路径：

- `_norm()` 用 OpenCC `t2s` 把繁体转简体，**但只有打分路径用它**
- `_bigrams()` 只做 `.lower()`，**不做繁简转换**

后果实测：

数据是繁体入库的（`chunk.text` 里是「訪客」「寵物」），学生用简体问「访客」，FTS 一个都匹配不到。而 `訪客` 能召回 9 条。

**当前为什么不炸？** 因为 `related_chunks()` 有兜底：FTS 返回空 → 落到 Python 打分，而那一层的 `_tokens()` 用了 OpenCC，繁简互通。**"主路径快一点，兜底路径正确"**，典型工程妥协。要修就得在 `_bigrams()` 里也调 `_norm()`，但那样每次建索引都要过一遍 OpenCC，导入 368 条会明显变慢——**留作已知限制，等真的出现大量漏检再改**。

### 4.5 为什么现在不用向量库

`app/retrieve.py` 开头直接写了答案：

```
为什么不用向量库：
- 现在只有 111 条，暴力算一遍不到 1 毫秒
- 繁简混用（数据繁体、学生简体会问）用 OpenCC 统一到简体再建索引
- 等 L2 网页切片进来（几千条），再换 sqlite-vec / pgvector，接口不变
```

展开看取舍：向量库要 embedding 模型 + 向量库 + 维度对齐，每条内容都得跑一次 embedding（368 条几分钟 + 真金白银的 token），离线就废，而且**只能给一个相似度分数，说不出命中了哪几个词**。反过来，BM25 + 二元组零依赖、可解释、断网可用，**弱在语义召回**——"能不能养猫"可能漏掉"飼養寵物"这种换说法的问法。

**核心判断：这个库的问题不是"召回不到"，而是"内容还不够全"。** 140 条问答覆盖不了学生所有问题，向量检索再强也变不出不存在的答案。所以优先级是把内容补全、把审核流程跑顺。

后门留得很清楚：`retrieve.py` 已经把检索封装成 `BM25` 类和 `tokenize()`，换实现只改 `search()` 内部，调用方不动。等 `chunk` 涨到几千条、或者 `qa_log` 里出现大量"字面不重合但语义相同"的漏检（`answer LIKE '%没有找到确切答案%'` 的那些），才是切换的信号。

## 6. 读写路径

### 6.1 所有连接都从 `connect()` 出来

```python
def connect(write: bool = False) -> sqlite3.Connection:
    config.DATA_DIR.mkdir(parents=True, exist_ok=True)
    conn = sqlite3.connect(config.DB_PATH, timeout=10)
    conn.row_factory = sqlite3.Row
    if write:
        conn.executescript(SCHEMA)
    return conn
```

四件事，每件都有理由：

**`config.DATA_DIR.mkdir(parents=True, exist_ok=True)`** —— 保证目录在。`exist_ok=True` 让它可重复调用，第一次部署时不会因为目录不存在而崩。

**`timeout=10`** —— 等锁最多 10 秒。SQLite 遇到写锁不是立刻报错，而是**重试 10 秒**，超时才抛 `database is locked`。10 秒够一个正常事务跑完了；如果你的写事务超过 10 秒，那本身就该优化。

**`row_factory = sqlite3.Row`** —— 让查询结果能按列名取（`r['question']`）而不是只能按下标（`r[0]`）。这是全项目敢写长 SQL 的前提：`SELECT *` 之后还能靠名字取字段，不用数位置。

**`write=True` 才执行 `SCHEMA`** —— 这是性能优化，也是隐患。读路径不跑 `executescript`（省掉每次解析 DDL 的开销）；但代价是**读连接不能建表**，如果库文件不存在，读连接会打开一个空库然后报 `no such table`。所以启动时必须先 `init_db()`。

```python
def init_db() -> None:
    with connect(write=True) as conn:
        conn.executescript(SCHEMA)
        _migrate(conn)
        # FTS 空了但有条款 → 回灌
        ...
        conn.commit()
```

### 6.2 `with connect()` 的真相：它**不关连接**

这是 Python 陷阱：**`sqlite3.Connection` 的 `with` 只负责事务**（正常退出 commit，异常退出 rollback），**不负责关闭连接**。实测：

```bash
.venv/Scripts/python.exe -c "
import sqlite3
c = sqlite3.connect('data/kb.sqlite3')
with c: pass
print(c.execute('SELECT 1').fetchone())   # 仍然可用
"
# (1,)
```

所以项目里满地的 `with connect() as conn:` 每调一次就**泄露一个连接**，直到 GC 回收。没出问题是因为：每次操作都是短连接，让 GC 收掉毫无压力；读连接开着不持锁；写连接在 `with` 退出时已提交并释放写锁，即使对象还活着也不挡人。

**但这是隐患**：如果哪天有人写长事务（`with connect(write=True) as conn:` 里跑 30 秒循环），那个连接会一直持写锁，其他写操作全部超时。**正确写法是 `with contextlib.closing(connect()) as conn:`**，但涉及全项目，暂不动——知道它存在就够了。

### 6.3 `_migrate()`：`CREATE TABLE IF NOT EXISTS` 最大的坑

建表语句写 `IF NOT EXISTS`，很多人以为这就"幂等"了。不是：

> **`CREATE TABLE IF NOT EXISTS` 只保证"表不存在就建"，绝不会修改已存在的表。** 你后来往 `SCHEMA` 里加一列，对老库完全无效——老库跑一遍 `executescript(SCHEMA)`，表已存在，跳过，新列不存在。

所以每个 `ALTER` 都要手写一遍：

```python
def _migrate(conn) -> None:
    """给老库补列（CREATE TABLE IF NOT EXISTS 不会改已存在的表）。"""
    cols = {r[1] for r in conn.execute("PRAGMA table_info(kb_item)").fetchall()}
    for name, decl in (("owner", "TEXT"), ("locked_until", "TEXT"),
                       ("version", "INTEGER NOT NULL DEFAULT 1"),
                       ("needs_recheck", "INTEGER NOT NULL DEFAULT 0")):
        if name not in cols:
            conn.execute(f"ALTER TABLE kb_item ADD COLUMN {name} {decl}")
```

**模式非常固定，四步：**

1. `PRAGMA table_info(表)` 拿到现有列名（`r[1]` 是列名，`r[0]` 是序号，`r[2]` 是类型）
2. 攒成 set，查得快
3. 逐个判断 `if name not in cols`
4. `ALTER TABLE ... ADD COLUMN`

**为什么要 `PRAGMA table_info` 而不是 `try/except`？**

```python
# 反面教材，别这么写
try:
    conn.execute("ALTER TABLE kb_item ADD COLUMN owner TEXT")
except sqlite3.OperationalError:
    pass
```

能跑，但会**吞掉真正的错误**——比如表名拼错、数据库只读、磁盘满，全被 `except` 吃掉了。用 `PRAGMA` 判断是"先看再做"，错误会正常抛出。

**`_migrate()` 里还有两类动作，性质不同：**

**加列 + 回填数据：**

```python
if "original_answer" not in kcols:
    conn.execute("ALTER TABLE kb_item ADD COLUMN original_answer TEXT")
    # 老条目：把当前答案当作原文留档，之后审核时能看出改了什么
    conn.execute("UPDATE kb_item SET original_answer = answer WHERE original_answer IS NULL")
```

**建表 + 回填 uid：**

```python
for table, prefix, textcol in (("kb_item", "kb", "question || char(10) || answer"),
                               ("chunk", "chunk", "text")):
    for r in conn.execute(f"SELECT id, {textcol} AS t FROM {table} WHERE uid IS NULL").fetchall():
        conn.execute(f"UPDATE {table} SET uid=?, revision=COALESCE(revision,1), content_hash=?"
                     " WHERE id=?", (f"{prefix}-{int(r['id']):04d}", _hash12(r["t"] or ""), r["id"]))
```

注意 `WHERE uid IS NULL` —— 只补空的行，已经有的不碰。**这是幂等的正确姿势**：不是"全部重算"，而是"只处理缺的"。

**一个真实的坑：`_migrate()` 是在 `init_db()` 里被调的，而 `init_db()` 只有在启动时跑。** 如果你手工用 `sqlite3` 打开库改了结构，下次启动 `_migrate()` 会把它"补回"到代码认为正确的样子——包括可能把你手工加的列留着、但代码不知道它。**结论：改结构只改 `app/db.py`，别手工 ALTER。**

### 6.4 事务与并发：SQLite 只有一个写者

这是理解所有并发问题的起点：

> **SQLite 的写锁是「数据库级」的，不是表级、不是行级。** 同一时刻，整个 `kb.sqlite3` 只能有一个写事务。

不是"两个人改不同条目可以并行"——是"一个人改第 3 条，另一个人连第 100 条都改不了"。

实测这条限制（在**拷贝**上做的，不碰真库）：

```bash
# 连接 A 开事务并写
a.execute('BEGIN IMMEDIATE')
a.execute("UPDATE kb_item SET note='x' WHERE id=1")
# 连接 B 也写
b.execute("UPDATE kb_item SET note='y' WHERE id=1")
```

真实报错：

```
OperationalError -> database is locked
```

而同一时刻 B **读**是成功的——读锁和写锁可以共存（多读者 + 单写者）。

**这个限制在本项目里为什么不是问题？** ① 写入全是"人点一下"，峰值并发不超过 3；② `timeout=10` 让冲突变成"排队等 10 秒"而不是立刻失败，真实等锁通常 < 100 ms；③ 没有长事务——最长的写操作是 `rebuild_chunk_fts()`（重建 368 条），几百毫秒，而且只在导入后手工调。

**`BEGIN IMMEDIATE` 是个值得记的技巧。** 默认的 `BEGIN` 是 **deferred**：先拿读锁，等第一次写才升级成写锁——这个升级过程可能失败（别人抢先了）。`BEGIN IMMEDIATE` 一开始就拿写锁，失败得早、失败得干净。`claim_item()` 那种"读-判-写"的操作，理论上应该用 IMMEDIATE。

**并发还靠两道闸。** 一是**乐观锁**：`decide_item()` 比对前端带来的 `version`，对不上就返回 `conflict`（"这条刚被别人改过，请刷新"），成功后 `version+1`——防止后保存的人静默覆盖先保存的人。二是 **`claim_item()` 的 30 分钟认领**：一条 SQL 里同时判断"锁过期 / 没人锁 / 是我锁的"，靠 `rowcount > 0` 判断抢到没有，这是 SQLite 里做原子"比较并交换"的标准手法。

### 6.5 发布/编辑时怎么写历史

`update_item()` 是唯一的编辑入口，只允许改白名单字段：

```python
APPROVED_FIELDS = {
    "question", "answer", "category", "source", "source_url", "source_type",
    "note", "status", "ttl_type", "audience", "owner", "reviewer",
    "verified_at", "valid_until", "warnings", "locked_until", "version",
    "needs_recheck", "source_anchor", "source_chunk_id",
}
```

**白名单不是洁癖，是安全边界。** 否则前端传一个 `{"id": 5}` 就能改主键，传 `{"uid": "x"}` 就能破坏对外契约。

```python
def update_item(item_id: int, patch: dict) -> dict | None:
    fields = {k: v for k, v in patch.items() if k in APPROVED_FIELDS}
    ...
    with connect(write=True) as conn:
        conn.execute(f"UPDATE kb_item SET {sets} WHERE id = ?", (*fields.values(), item_id))
        bump_kb_revision(conn, item_id, changed_by=..., note=...)
        conn.commit()
```

**关键：`UPDATE` 和 `bump_kb_revision` 在同一个连接、同一个事务里。** 要么都成功，要么都回滚——不会出现"内容改了但历史没记"。

```python
def bump_kb_revision(conn, item_id: int, changed_by: str = "", note: str = "") -> None:
    """内容真变了才 +1；旧版写进 kb_revision。"""
    row = dict(conn.execute("SELECT * FROM kb_item WHERE id=?", (item_id,)).fetchone())
    new_hash = _hash12(f"{row.get('question','')}" + chr(10) + f"{row.get('answer','')}")
    if new_hash == (row.get("content_hash") or ""):
        return                                    # 内容没变，直接返回
    rev = int(row.get("revision") or 1)
    conn.execute(
        "INSERT OR REPLACE INTO kb_revision (uid, revision, content_hash, question, answer, status,"
        " changed_by, changed_at, note) VALUES (?,?,?,?,?,?,?,?,?)",
        (row.get("uid") or f"kb-{item_id:04d}", rev, row.get("content_hash") or "", ...))
    conn.execute("UPDATE kb_item SET revision=?, content_hash=? WHERE id=?",
                 (rev + 1, new_hash, item_id))
```

**"内容真变了才 +1"是这整段的核心。** 只改 `reviewer`、只改 `note`、只改 `status`（审核通过），hash 不变，`revision` 不动。这条规则防止"审核一次涨一版"，让 `revision` 真正代表**内容的代数**。

**⚠️ 一个真实的边角（我在拷贝库上验证过，没有改代码）：**

`bump_kb_revision()` 是在 `UPDATE kb_item` **之后**被调用的。所以它 `SELECT` 出来的是**新内容**，而 `row["content_hash"]` 还是**旧 hash**。结果是：写进 `kb_revision` 的那一行，用的是新正文 + 旧 hash + 旧 revision 号。

在 `data/kb.sqlite3` 的副本上实测：改第 3 条的答案 → `kb_item.revision` 从 1 变 2、hash 从 `8a7d7428db7f` 变 `a677232af7a0`，而 `kb_revision` 里那行是 `('kb-0003', 1, '8a7d7428db7f', <新正文>)`。也就是说**历史表里存的是新内容，标着旧版本号**——按 `(uid, revision)` 回查，取不到改之前的原文。

为什么至今没暴露？因为**线上 `kb_revision` 是 0 行**：140 条数据都是导入生成的（`uid` 由 `_migrate()` 回填），此后没有一条走过"编辑已发布条目并真的改了正文"的路径。

这不是本文要修的东西，但**记在这里**：真要靠历史表做"申诉时调出旧答案"，得先把顺序理顺——先读快照、再 UPDATE、再把**旧快照**写进历史表。**在修之前别把 `kb_revision` 当可靠审计来源；可靠的是 `review_log.before`**（那份快照由 `decide_item` 在改动前取，顺序是对的）。

### 7.1 备份：启动时自动拷一份

`scripts/start_all.bat` 里这段：

```bat
rem 每次启动先备份数据库，避免误删/误操作丢库
if not exist backups mkdir backups
if exist data\kb.sqlite3 powershell -NoProfile -Command "Copy-Item 'data\kb.sqlite3' ('backups\kb-' + (Get-Date -Format 'yyyyMMdd-HHmm') + '.sqlite3')" >nul 2>&1
```

三个细节值得注意：**① 备份发生在启动服务之前**——顺序很重要，先拷再拉 `uvicorn`，备份的一定是"上一个稳定状态"；**② 文件名带时间戳到分钟**（`yyyyMMdd-HHmm`），不会互相覆盖；**③ 在 `journal_mode=delete` 下 `Copy-Item` 就是完整备份**，因为事务结束后没有残留的 `-wal`。**哪天切了 WAL，这一句必须改成 `sqlite3 data\kb.sqlite3 ".backup backups\kb-xxx.sqlite3"`**，否则会拷到"缺了最新事务"的库。

当前备份目录实测两份：

```
kb-20261112-1021.sqlite3   102400 字节  25 页   kb_item=118  chunk=0
kb-20261123-1257.sqlite3   712704 字节 174 页   kb_item=135  chunk=368
```

**从这两份能读出一部项目史**：11 月 12 日的库只有 25 页、`chunk` 还是 0 条——那时候问答条目已经导入了，规章还没进来。11 月 23 日的 174 页、`chunk=368`——规章导入完成。现在是 269 页、`kb_item=140`。

**这就是为什么备份不能只看"最新一份"。** 如果 11 月 23 日那次导入把旧的 118 条问答覆盖坏了，`kb-20261112-1021` 是唯一的退路。

### 7.2 恢复演练：备份不验证等于没有备份

`scripts/restore_check.py` 干的事，一句话：**把备份真的开一次，确认能读、能查。**

```bash
.venv/Scripts/python.exe scripts/restore_check.py
# 或指定某一份
.venv/Scripts/python.exe scripts/restore_check.py backups/kb-20261123-1257.sqlite3
```

它做六件事：

```python
tmp = Path(tempfile.mkdtemp(prefix="restore_"))
dst = tmp / "kb.sqlite3"
shutil.copy2(src, dst)                              # ① 拷到临时目录，不动线上

ok = con.execute("PRAGMA integrity_check").fetchone()[0]
check("完整性检查通过", ok == "ok", str(ok))          # ② 完整性

counts = {t: con.execute(f"SELECT COUNT(*) FROM {t}").fetchone()[0]
          for t in ("kb_item", "chunk", "library_item", "upload_file")}
check("问答条目 > 0", counts["kb_item"] > 0)          # ③ 有没有数据
check("规章条款 > 0", counts["chunk"] > 0)

cols = {r[1] for r in con.execute("PRAGMA table_info(chunk)")}
if "anchor" not in cols:
    check("备份结构是当前版本", False, "旧结构缺 anchor/version，恢复后要跑迁移")  # ④ 结构新旧

os.environ["DATA_DIR"] = str(tmp)
from app import db                                   # ⑤ 真的跑一次检索
hits = db.related_chunks("換房間", limit=3)
check("换房间能检索到条款", bool(hits))

shutil.rmtree(tmp, ignore_errors=True)               # ⑥ 清理
```

**四个设计意图，每个都对应一种真实事故：**

- **拷到临时目录**：绝不在线上库上跑检查。`integrity_check` 本身只读，但万一脚本有 bug 也不伤生产数据。
- **检查结构（`anchor` 列在不在）**：最容易被忽略的一条。一份能打开、`COUNT(*)` 也正常的备份，可能是**旧结构**——恢复后应用一跑就 `no such column`。脚本会明确说"这份备份太旧，别拿它当恢复依据"。
- **真的跑一次检索**（`db.related_chunks("換房間")`）：`COUNT(*)` 只能证明"行在"，不能证明"索引能用"——FTS 坏了、`chunk_fts` 空了，`COUNT(*)` 一样正常。
- **`os.environ["DATA_DIR"]` 必须在 `from app import db` 之前设**：`config.py` 在 import 时就计算 `DB_PATH`。这是真实的时序陷阱，代码里也写了注释。

### 7.3 VACUUM：把文件真正缩小

删除不会缩小文件——被删的页留在 freelist 里等复用。要真正还给磁盘：

```bash
.venv/Scripts/python.exe -c "
import sqlite3
c = sqlite3.connect('data/kb.sqlite3')
print('前:', c.execute('PRAGMA page_count').fetchone()[0], '页 /',
             c.execute('PRAGMA freelist_count').fetchone()[0], '空闲')
c.execute('VACUUM')
print('后:', c.execute('PRAGMA page_count').fetchone()[0], '页')
"
```

**`VACUUM` 到底做了什么：** 新建一个空库，把有用的页整块搬过去，再替换原文件。所以它是**全库重写**而不是"整理碎片"——269 页跑一次几十毫秒，几 GB 的库会跑很久且需要**等量临时空间**；跑的时候**独占整个库**，其他连接全部阻塞；**必须在没有活跃写事务时跑**，否则报 `cannot VACUUM - SQL statements in progress`；之后 `page_count` 会变（有 `AUTOINCREMENT` 的表 `rowid` 不会变，因为 `sqlite_sequence` 保住了计数器）。

**什么时候该跑：** `freelist_count / page_count` 明显大于 0（比如删了大量 `qa_log` 之后）。当前是 `0 / 269`，**完全没必要刷**。

**`auto_vacuum` 是另一条路**，能在每次提交时自动收缩，代价是运行时开销和文件碎片。当前 `auto_vacuum=0` 是对的——定期手工 `VACUUM` 比每次写都付代价划算。

## 8. 常见故障与排查

### 8.1 `database is locked`

**症状：** 写操作（审核、投稿、记日志）偶发失败，报 `sqlite3.OperationalError: database is locked`。

**根因（按概率排）：** ① **写事务没提交**——某段代码 `connect(write=True)` 后忘了 `commit()`，连接没被回收，写锁一直持着；② **长事务**，批导入时一边导一边有人用；③ **别的进程开着库**，比如 DB Browser 里有个未提交的 `UPDATE`；④ **网盘同步锁文件**（本项目在 `D:\Projects\` 本地盘，没这个问题）。

**排查：**

```bash
ls -la data/kb.sqlite3*      # ① 有残留 journal = 上次崩溃了
# ② 有没有别的进程占着库？用 handle.exe 或资源监视器搜 kb.sqlite3
# ③ 自己的进程里漏了 commit？看 data/server.err 里报错前后的调用栈
```

### 8.2 `no such column: xxx`

实测报错长这样：

```bash
.venv/Scripts/python.exe -c "
import sqlite3; c=sqlite3.connect('data/kb.sqlite3')
c.execute('SELECT owner_name FROM kb_item LIMIT 1')
"
# sqlite3.OperationalError: no such column: owner_name
```

**两种根因，处理方式相反：**

**① SQL 里列名写错了。** 拿真实列名一比对就知道：

```bash
.venv/Scripts/python.exe -c "
import sqlite3; c=sqlite3.connect('data/kb.sqlite3')
print([r[1] for r in c.execute('PRAGMA table_info(kb_item)')])
"
```

**② 代码加了新列，但库没迁移**——通常是"老库 + 新代码"，或备份恢复后没跑迁移。修复：

```bash
.venv/Scripts/python.exe -c "from app.db import init_db; init_db(); print('迁移完成')"
```

**为什么安全？** `_migrate()` 全是 `if name not in cols` 的加法：只加列、不删列、不改类型、不动数据（除补空的 `uid`）。**跑一百次结果一样。**

### 8.3 FTS 索引为空

**症状：** 条款明明在库里（`chunk` 有 368 行），搜什么都搜不到，`related_chunks()` 永远走 Python 兜底打分。

```bash
.venv/Scripts/python.exe -c "
import sqlite3; c=sqlite3.connect('data/kb.sqlite3')
print('chunk    :', c.execute('SELECT COUNT(*) FROM chunk').fetchone()[0])
print('chunk_fts:', c.execute('SELECT COUNT(*) FROM chunk_fts').fetchone()[0])
print('样例 body:', c.execute('SELECT substr(body,1,60) FROM chunk_fts LIMIT 1').fetchone())
"
```

三种状态：`368 / 368` 正常；`368 / 0` 索引空了；`368 / 368 但搜不到` 说明 `body` 是空串或没切好。后两种都要回灌：

```bash
.venv/Scripts/python.exe -c "from app.db import rebuild_chunk_fts; print('回灌', rebuild_chunk_fts(), '条')"
```

`rebuild_chunk_fts()` 干的事：`DELETE FROM chunk_fts` → 读所有 `published` 条款 → `_bigrams(title + text)` → 批量 `INSERT`。

**索引为什么会空？** 两条真实路径：① **导入脚本只写了 `chunk`，没重建 FTS**（所以每次导入新条款后必须调一次）；② **`chunk_fts` 被 DROP 后重建了**（虚拟表删除会连带删影子表，重建时是空的）。

`init_db()` 里有自动兜底：**"FTS 空 + 有已发布条款" → 启动时自动回灌**。所以最省事的修复其实是**重启一次服务**。

### 8.4 附件 404：`path` 与 URL 的对应关系

这条链路有三段，断在哪段要一段段查：

```
upload_file.path          "files/inbox/202611/9951e49718b2.png"
        ↓  "/files/" + path.split("files/", 1)[-1]
返回给前端的 url           "/files/inbox/202611/9951e49718b2.png"
        ↓  StaticFiles(directory=config.FILES_DIR)  =  data/files
磁盘上的真实位置           data/files/inbox/202611/9951e49718b2.png
```

逐段验证：

```bash
.venv/Scripts/python.exe -c "
import sqlite3; c=sqlite3.connect('data/kb.sqlite3')
for r in c.execute('SELECT id, path FROM upload_file'): print(r)"
ls -la data/files/inbox/202611/          # 文件在不在
curl -sI http://127.0.0.1:8001/files/inbox/202611/9951e49718b2.png | head -3
```

**四个最常见的断点：**

**① 只恢复了数据库，没恢复 `data/files/`**（见 7.5）。`path` 记得很清楚，文件没了。

**② `path` 存成了绝对路径。** 若哪天有代码写 `str(dest)` 而不是 `dest.relative_to(config.DATA_DIR).as_posix()`，库里会变成 `D:\Projects\...\files\inbox\...`，换机器后前缀全错。**这种最隐蔽，因为在本机测试永远正常。**

**③ `split("files/", 1)[-1]` 匹配不到。** 这写法靠字符串里**恰好有一次 `files/`**；若变成 `data/files/files/inbox/...`，`[-1]` 拿到 `inbox/...`，前缀丢了 → 404。

**④ URL 里的中文/空格没编码。** 当前文件名都是 `sha[:12] + ext`（纯 ASCII），不会遇到；**一旦改成保留原始文件名就会踩 URL 编码的坑**。

### 8.5 一张排查速查表

| 现象 | 最可能的原因 | 第一条命令 |
|---|---|---|
| `database is locked` | 有未提交的写事务 / 别的进程占着 | `ls -la data/kb.sqlite3*` |
| `no such column` | 老库没迁移 / 列名拼错 | `PRAGMA table_info(表)` |
| 搜不到条款 | FTS 空了 / 繁简不匹配 | `SELECT COUNT(*) FROM chunk_fts` |
| 附件 404 | `data/files/` 没拷 / path 格式变了 | `ls data/files/inbox/` |
| 文件很大但没数据 | freelist 没回收 | `PRAGMA freelist_count` |
| 备份"能用"但恢复后报错 | 备份是旧结构 | `scripts/restore_check.py` |
| 页面空白 / 500 | 先看 `data/server.err` 尾部 | `tail -30 data/server.err` |

## 10. 速查与术语

### 10.1 术语表

| 术语 | 一句话解释 |
|---|---|
| **页（page）** | SQLite 最小读写单位，默认 4096 字节，文件就是页的序列 |
| **B-tree** | 表与索引的底层结构，让"按 rowid 找一行"只走 log(N) 层 |
| **rowid** | 每行的隐藏整数主键；`INTEGER PRIMARY KEY` 会直接复用它 |
| **rollback journal** | 写前把原页拷到 `-journal`，提交后删除；当前模式 |
| **WAL** | Write-Ahead Log，写进 `-wal`，读写可并行；**本项目未启用** |
| **freelist** | 被删除但未归还磁盘的页的链表 |
| **VACUUM** | 全库重写，把 freelist 真正还给磁盘 |
| **FTS5** | SQLite 的全文索引虚拟表；本项目用自建二元组分词 |
| **影子表** | FTS5 自动生成的 `_data`/`_idx`/`_content`/`_docsize`/`_config` |
| **bm25** | 全文排序算法；`bm25()` 返回负数，越小越相关 |
| **bigram** | 相邻两字的滑窗切片，本项目的中文分词方案 |
| **乐观锁** | 提交时比对版本号，不一致就拒绝——`kb_item.version` |
| **幂等** | 重复执行结果不变；`_migrate()` 和 `INSERT OR REPLACE` 靠它 |
| **uid** | 永不变的内容编号（`kb-0003`），对外契约的一部分 |
| **revision** | 内容第几版，只有正文 hash 变了才 +1 |
| **软链接** | 只存 id、不建外键的引用（如 `library_item.candidate_id`） |

### 10.2 收尾：这个库最值得学的三件事

**第一，"一个文件"不是简陋，是一种承诺。** 1 MB 里装着 368 条规章、140 条审核过的问答、44 条院生作品、880 次真实提问的痕迹，可被 `Copy-Item` 备份、被 U 盘带走、在断网机器上跑起来——这种可携带性，是很多项目上云之后才怀念的东西。

**第二，并发问题的答案在"写入点在哪"。** 单写者听起来吓人，但本项目写入全是"人点一下"，所以它从来不是瓶颈。**先想清楚谁是写者、多久写一次，再决定要不要换数据库**——顺序不能反。

**第三，最危险的不是 bug，是"看起来正常"。** 6.5 那处问题线上 0 行、测试全过、`integrity_check` 返回 `ok`，因为那段代码从没被真正执行过。`restore_check.py` 里"备份结构是不是当前版本"那一条防的也是同类事故：**能打开、能 count、但恢复之后不能用。**
