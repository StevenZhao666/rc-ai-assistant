02一次提问经过什么（八步）

  1. 识别身份：请求头里的学号（7 位）＋设备号，决定限额档。
  2. 安全优先：代写、医疗、情绪、安全、跨书院 → 专用话术，不检索。
  3. 实时与缺口拦截：天气走气象局；押金、门禁这类确知没有的直接说去哪问。
  4. 意图判断：命中很强就直接查资料；否则让模型判“要不要查”。闲聊直接回，不占额度。
  5. 检索：繁简归一 → 中文二元组 → BM25 → 取分数最高的几条。
  6. 生成：只给模型这几条资料，要求句末标 [n]，不许编。
  7. 溯源：只展示模型真正引用的条目；若它漏标，仍挂出最相关那一条。
  8. 记账：qa_log 记模式、耗时、引用数；llm_usage 记 token。

04数据库现状（6 张表，SQLite）

核心思路：一条知识＝一条断言；检索只吃 published 且未过期的；原文与问答分开存。
表存什么关键字段与谁关联
kb_item问答条目：问题、答案、来源、状态、时效、绑定条款 status ttl_type source_url original_answer source_chunk_id → chunk（依据）
→ review_log
chunk条款级原文：手册、房间规定，一段一条 anchor section variant version hash ← kb_item.source_chunk_id
qa_log每次提问：谁、问什么、答什么、什么模式、多久、引用几条 mode latency_ms session_id n_cites → 未命中/看板
feedback👍/👎 与用户写的原因 vote note mode → kb_item（按问题）
review_log审批留痕：谁、何时、对本条做了什么（含 autobind/bind） action reviewer before after → kb_item / candidate
candidate从官网抓来、还没成条目的候选 url status item_id → kb_item（转化后）
问答层（可审核、可改） 原文层（只加不改） 行为记录（只追加）

05未来的书院数据库（设想，未实施）

目标：不只服务崑崑，还能给别的项目、同学的 AI 用。关键是分层和版本。
三层，从下往上
① 原文层规章/通知/手册，带版本与生效、废止日期。只加不改，任何历史版本可回溯。
② 知识层QA 条目、术语表、常见误解。每条指向原文层的一段，可审核。
③ 入口层API / MCP：谁能拿什么、限流、审计。
↓ 需要新增的表（草图）
表（设想）作用为什么需要
doc一份文件：标题、类型、发布机构、版本、生效/废止日期、文件哈希现在版本信息散在 chunk 字段里，无法回答“这条何时失效”
doc_version文件的一次修订：版本号、发布日期、原文文件规章会改版，学生可能引用旧版
clause条款：doc_version + 条款号 + 正文 + 语言现在 chunk 兼任，字段越来越挤
kb_item_ref问答 ↔ 条款 的多对多，带“依据强度”（直接规定 / 解释 / 参考）一条问答可能靠两条条款；现在只能绑一条
client调用方：名称、类型（内部/学生/外部）、密钥、scope、限流对外开放必须有身份与配额
api_log对外调用记录：谁、问什么、返回哪些条目、耗时出事能追；也能统计哪些内容最常被查
glossary书院术语（HA、RC、High Table…）与解释学生问“什么是 HA”，现在靠条目凑
对外只读接口建议先只开四个：search_kb、get_item、get_clause、list_updates；MCP 就是把它们在协议层包一层。
