CKLC · RC AI ASSISTANT · 系统关系

@@昆昆@@问答 × 书院资料库

两个子专案跑在同一台 2C4G 主机、同一个 FastAPI 进程、同一个 SQLite 档里。 真正分开的是主数据表与使用路径；真正共用的是底座（资料库连线、身分、双语）。 三张图按软体工程常用图种画：边界 → 依赖 → 资料流。

一眼看懂的关系

两者不是「两个网站互相呼叫」，而是同一个网站里的两组路由。 学生一边问答、一边逛资料库；审阅人一边审问答条目、一边审投稿档案，用的是同一套身分。

为什么要合并部署

主机只有 2 核 4G。合并成一个进程共用一个 SQLite，省掉一份记忆体与一份连线池； 代价是两边的发布绑在一起，改一边要重启整个服务。

图 02

模组依赖图

这张图回答：从程式码看，谁依赖谁？哪条依赖是「共用」，哪条是「耦合」？

读图方法：箭头 = 呼叫／引用；粗红虚线 = 跨子项目的 HTTP 呼叫（代码不互相 import）；底部横条 = 两个子专案都依赖的底座。

import / 直接呼叫 跨子专案（HTTP） 底座被 A、B 同时 import

A 与 B 之间没有 import

review.py 与 answer.py 互不引用。唯一的桥是 HTTP： MCP 服务用 urllib 打 /api/search，而不是把 db.py 拉进来。

底座是共用而非继承

两边都 import db.py，但用的是不同函式：A 走 search()， B 走 library_items()、search_all()。共用连线与表结构，不共用业务逻辑。

图 03

资料流图

这张图回答：一条资料从哪里进来、经过什么、最后给谁看？两条链在什么地方汇合，又在什么地方不汇合？

读图方法：上行 = 问答知识库（离线重建），下行 = 资料库（线上投稿与抓取）。两条泳道各自闭环，只在最底部两个出口汇合。

完全不读 library_item；资料库条目也不会被 BM25 当成答案依据。分开是设计，不是遗漏。 汇合是「查询层」的汇合，不是「资料层」的打通 两张表各自独立 没有外键、没有同步
线上即时 离线脚本 粗框 = 两条链各自的「已发布」闸门

共同点：都有一道 published 闸门

两边都是「先落地、再审核、发布后才对外」。问答审的是条目与条款， 资料库审的是院生投稿。检索层都只读 status='published'，草稿永远搜不到。

不同点：更新节奏

问答靠 Excel 全量重建（离线、可控）；资料库靠投稿与抓取，随时增长。 所以问答用 ttl_type 管有效期，资料库用 reviewed_at 管新鲜度。
