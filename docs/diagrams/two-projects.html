CKLC · RC AI ASSISTANT · 系統關係

崑崑問答 × 書院資料庫

兩個子專案跑在同一台 2C4G 主機、同一個 FastAPI 進程、同一個 SQLite 檔裡。 真正分開的是主數據表與使用路徑；真正共用的是底座（資料庫連線、身分、雙語）。 三張圖按軟體工程常用圖種畫：邊界 → 依賴 → 資料流。

rc-ai-assistant · v0.2.0 · 依 2026-11 本機與線上實況 · 所有節點皆可在 repo 中找到對應檔案

系統邊界圖

這張圖回答：哪些東西屬於這個系統，哪些在外面？兩個子專案是怎麼被裝進同一個盒子裡的？

讀圖方法：虛線大框 = 一個部署單元；框內兩個虛線小框 = 兩個子專案；底部實線條 = 兩者共用的底座；框外人形 = 使用者與外部系統。

系統內呼叫 離線或非同步 虛線大框 = 一個部署單元

一眼看懂的關係

兩者不是「兩個網站互相呼叫」，而是同一個網站裡的兩組路由。 學生一邊問答、一邊逛資料庫；審閱人一邊審問答條目、一邊審投稿檔案，用的是同一套身分。

為什麼要合併部署

主機只有 2 核 4G。合併成一個進程共用一個 SQLite，省掉一份記憶體與一份連線池； 代價是兩邊的發布綁在一起，改一邊要重啟整個服務。

圖 02

模組依賴圖

這張圖回答：從程式碼看，誰依賴誰？哪條依賴是「共用」，哪條是「耦合」？

讀圖方法：箭頭 = 呼叫／引用；粗紅虛線 = 跨子項目的 HTTP 呼叫（代碼不互相 import）；底部橫條 = 兩個子專案都依賴的底座。

import / 直接呼叫 跨子專案（HTTP） 底座被 A、B 同時 import

A 與 B 之間沒有 import

review.py 與 answer.py 互不引用。唯一的橋是 HTTP： MCP 服務用 urllib 打 /api/search，而不是把 db.py 拉進來。

底座是共用而非繼承

兩邊都 import db.py，但用的是不同函式：A 走 search()， B 走 library_items()、search_all()。共用連線與表結構，不共用業務邏輯。

圖 03

資料流圖

這張圖回答：一條資料從哪裡進來、經過什麼、最後給誰看？兩條鏈在什麼地方匯合，又在什麼地方不匯合？

讀圖方法：上行 = 問答知識庫（離線重建），下行 = 資料庫（線上投稿與抓取）。兩條泳道各自閉環，只在最底部兩個出口匯合。

完全不讀 library_item；資料庫條目也不會被 BM25 當成答案依據。分開是設計，不是遺漏。 匯合是「查詢層」的匯合，不是「資料層」的打通 兩張表各自獨立 沒有外鍵、沒有同步
線上即時 離線腳本 粗框 = 兩條鏈各自的「已發布」閘門

共同點：都有一道 published 閘門

兩邊都是「先落地、再審核、發布後才對外」。問答審的是條目與條款， 資料庫審的是院生投稿。檢索層都只讀 status='published'，草稿永遠搜不到。

不同點：更新節奏

問答靠 Excel 全量重建（離線、可控）；資料庫靠投稿與抓取，隨時增長。 所以問答用 ttl_type 管有效期，資料庫用 reviewed_at 管新鮮度。

證據來源：app/main.py 路由器註冊 · app/db.py 建表與 search_all() · app/retrieve.py（不引用 library）· app/library.py /api/updates · mcp_server.py（走 HTTP）· systemd 三個單元 8091 / 8092 / 8093。 圖中未出現的元件，程式碼裡確實沒有；本圖不做推測性擴充。
